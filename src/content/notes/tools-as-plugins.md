后面想接的东西会越来越杂：搜歌、试听、抖音视频提取、图片处理、格式转换。如果每个都写一个页面、一个接口、一套错误处理，很快就没法维护了。

所以先定了一个很小的插件契约。

## 一个插件由三部分组成

- `manifest.ts`：纯数据。工具名、说明、状态、action 列表、每个 action 的输入字段。
- `server.ts`：可选。需要联网、需要密钥、需要绕开 CORS 的 action 放这里。
- `Tool.astro`：界面。可以用原生脚本，也可以用任何 Astro 支持的框架。

manifest 是唯一的真相。工具列表、API 校验、MCP 的 tool schema 都从它生成，不维护第二份。

## action 是边界

每个 action 有 id、标题、输入 schema。输入校验是一个很小的函数，不依赖 zod；字段类型、必填、长度、枚举都在 manifest 里写清楚。

服务端只做三件事：校验、限流、调用。插件作者拿到的是已经校验过的普通对象，不用关心 HTTP。

## 为什么 MCP 能直接复用

MCP 服务端不复制业务逻辑，它启动时读取门户的 `/plugins.json`，把每个 action 注册成一个 MCP tool，调用时转发到 `/api/tools/<plugin>/<action>`。

这样加一个工具只需要改插件目录，不用再改 MCP 服务端。搜索和读页面也一样，走门户的 `/search-index.json` 和 `/api/search`。

## 目前的三个例子

- **音乐**：按多个音源顺序搜索，第一个有结果就停；下载标准音质 MP3，有歌词时一起打包。
- **开发者工具**：JSON 格式化、时间戳、Base64、哈希。大部分在浏览器里算，哈希放服务端。
- **媒体解析**：先做 Open Graph 预览；真正的视频地址交给可配置的解析服务。没配置就明确告诉用户，不假装能解析。

第三个是刻意的：抖音这类站点的解析接口很不稳定，也比较敏感。把接口做成配置项，比在代码里塞一个随时会坏的 scraper 更诚实。
